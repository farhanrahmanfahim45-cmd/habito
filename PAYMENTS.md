# Payments — internal note

Not for the i2i application. The working record of what is built, what is
simulated, and exactly what has to change to make it real.

## Why the gateway is not wired up

SSLCommerz authenticates with a **store id and store password**. Habito is a
Vite single-page app: anything it holds ends up in a bundle the browser can
read. Putting those credentials in the client would hand anyone the ability to
initiate payments against the merchant account.

So a real payment must be started by something server-side. There are two other
blockers behind that one, and both are about the project, not the code:

- A live SSLCommerz account needs a **trade licence and a company bank
  account**. Habito has no legal entity.
- EMI has to be enabled separately through a merchant agreement.

## What is built

Everything that is not the gateway call:

- `rent_invoices` — one row per month of a confirmed booking, generated by a
  trigger. Owners can waive or adjust; nobody can mark one paid by hand.
- `payments` — extended with `invoice_id`, `kind` and `simulated`.
- Receipts — sequential, `HAB-2026-000001`, issued only when a payment
  succeeds.
- `mark_overdue_invoices()` — overdue is derived from the date, not a status
  someone remembers to set.

**The guards, all tested against Postgres as two separate users:**

| Attempt | Result |
|---|---|
| Renter inserts a payment already marked `successful` | Refused — a payment starts pending |
| Owner marks an invoice paid with no payment | Refused |
| Owner marks it paid citing a *failed* payment | Refused |
| Owner waives a month | Allowed |
| Gateway settles a pending payment | Invoice paid, receipt issued |

That last column is the point: a receipt can only exist behind a payment that
actually succeeded.

## What is simulated

One function, `payInvoice`, does two things: raises a pending payment, then
marks it successful. **The second half is the gateway's job.** It sets
`simulated = true`, and the interface says so in three places — a banner on the
rent page, a line in the payment dialog, and a line on the receipt itself.

Never clear `simulated` by hand. A real payment is one a gateway confirmed.

## Making it real

Write a Supabase Edge Function holding the credentials as secrets. The client
stops settling payments; it only ever creates them as pending.

**Initiate** — client calls the function with an invoice id. The function reads
the invoice server-side (never trusting a client-sent amount), creates the
pending `payments` row, calls SSLCommerz `/gwprocess/v4/api.php`, and returns
the redirect URL.

**Confirm** — SSLCommerz posts to an IPN endpoint. The function must:

1. Validate against SSLCommerz's own validation API using the `val_id`. Do not
   trust the POST body alone — this is the step people skip and it is the one
   that matters.
2. Check the amount and currency match the invoice.
3. Update `payments.status` to `successful` or `failed`, set `reference` and
   `gateway_payload`, and leave `simulated` false.

Everything downstream — invoice paid, receipt number, booking confirmed —
already happens on that update. No other code changes.

**Test cards** are in the SSLCommerz sandbox documentation. The sandbox needs no
trade licence, so the Edge Function can be written and tested long before the
entity exists.
